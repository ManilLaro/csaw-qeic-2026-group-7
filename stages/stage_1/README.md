# Stage 1 — Execution Stack Forensics

**100 points**

## Objective

Determine whether the supplied execution stack faithfully realized the intended
computation. Establish the strongest supported integrity verdict, locate any
failure boundary, reject incidental anomalies, and propose a repair and a way
to validate it. All execution is simulation-based; no physical hardware or
live IBM service access is required.

## Artifacts provided

artifacts/ contains intended_circuit.qpy, compiled_circuit.qpy, current and
historical mapping records, schedule.json, control_manifest.json, current and
previous calibration snapshots, execution logs/counts, historical counts and
backend information. Compare semantics and provenance across these records.
Do not edit them. Internal artifact IDs identify records and should be cited
exactly when needed.

## Questions to answer

- Are intended and compiled operations consistent?
- Do current mapping and scheduling records agree?
- What control/calibration provenance supports the claimed execution?
- Which logical operation and physical resources are implicated, if any?
- Which anomalies are incidental, and what evidence rejects them as causes?
- What diagnostic evidence supports your conclusion?
- What repair do you propose, and how would you validate repaired behavior?

Optional local diagnostic probes must obey diagnostic_budget.json. The supplied
diagnostic_client.py validates QPY probe structure and limits without executing
the probe. For example, from artifacts/:

```sh
python diagnostic_client.py probe.qpy --physical-qubits 0 1 --shots 500
```

Record any optional local experiments accurately in diagnostic_evidence. Static
artifact inspection is unmetered. No external diagnostic service is needed.

## Submission expectations

Implement solve_stage1(stage_dir) in the root solve.py. Use the root
submission_schema.json for the result format; a case-specific schema among
the artifacts does not replace it. Cite artifact paths relative to artifacts/,
with claims and optional record locators. Partial responses are valid; explain
uncertainty and support each milestone independently where possible.

Submit solve.py and outputs/result.json generated by the root evaluate.py.
The public validator checks structure and hashes. Organizers assign correctness
points using the rubric above. Stage 1 and Stage 2 total 200 core points;
the optional +30 bonus raises the maximum to 230.
